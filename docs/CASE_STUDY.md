# The-Wraith Case Study

## Baseline

The project began as a v0-generated fictional pirate-ship storefront. Its initial value was visual and conceptual: a strong theme, a product presentation, and a deployment-ready frontend baseline.

## Evolution

Subsequent reviewed changes turned that baseline into a broader delivery demonstration:

1. **Clarity and trust:** ship specifications became visible, mobile content became reachable, vulnerable dependencies were remediated, pnpm was pinned, and the checkout became an explicitly fictional charter that transmits nothing.
2. **State and sharing:** selected ships and views became URL-addressable with safe fallbacks.
3. **Interactive product work:** Rift Run added deterministic encounters, ship-specific doctrine, keyboard and touch input, accessible announcements, outcomes, logs, replay, and shareable state.
4. **Privacy and accessibility:** application analytics were removed, browser zoom was restored, and shared links gained descriptive metadata.
5. **Defect discovery:** browser verification exposed that daily seeds lost their day during sanitization; the complete UTC date is now preserved.
6. **Engineering evidence:** this foundation makes architecture, limitations, decisions, verification, and responsibility boundaries visible.

## Human and agent roles

Agents inspect, propose, implement, document, verify, and prepare pull requests within explicit scope. The human sets direction, reviews evidence, merges changes, and retains authority over production, external services, billing, destructive actions, and real data collection.

## Demonstrated capabilities

- Product iteration from an AI-generated baseline
- Responsive and accessible React interface work
- Deterministic client-side state reconstruction
- Safe URL input boundaries and shareable application state
- Privacy-conscious fictional interactions
- Dependency remediation and reproducible package management
- Branch, pull-request, preview, and review workflows
- Honest limitation tracking and architecture decision-making

## Evidence standard

The case study distinguishes repository evidence from inference. A statement about a deployed component must be supported by code or visible configuration. Proposed architecture is never presented as current. Manual checks are not described as automated coverage.

## Current gaps

- Broader component and end-to-end coverage beyond the committed deterministic engine regression suite
- Repository-owned CI
- Interactive reconstruction inspector
- Architecture tradeoff explorer
- Reliability and capacity simulations

These gaps form the roadmap; they are not hidden behind completed-sounding language.
